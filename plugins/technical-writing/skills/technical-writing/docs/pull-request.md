# PRの概要の書き方

レビュー担当者が、変更の妥当性を判断できる概要を書く。
共通の進め方は [作成の流れ](writing-flow.md) に従う。
文章は [執筆の指針](../SKILL.md) に沿って整える。

## 書く前に確認すること

- リポジトリのPRテンプレートと記載ルールを読む。
- ベースブランチとの差分全体を確認する。
- 関連するIssueや仕様から、解決する問題を確認する。

## テンプレートに従う

PRの本文は、原則としてリポジトリのテンプレートに従う。
GitHubでは、リポジトリ内のテンプレートファイルを探して読む。

### GitHubで確認する場所

- `.github/`、リポジトリのルート、`docs/`を確認する。
- `PULL_REQUEST_TEMPLATE.md`などのファイルを探す。
- `PULL_REQUEST_TEMPLATE/`内の複数テンプレートも確認する。

### テンプレートの適用

- 複数ある場合は、変更の用途に合うテンプレートを選ぶ。
- 指定された見出し、必須項目、チェックリストを維持する。
- 以下の記載内容は、テンプレートの該当項目に書く。
- チェック項目は、実際に確認できたものだけを完了にする。
- テンプレートがない場合は、末尾の構成例を使う。

検証結果はCIで確認するため、本文に独自の検証欄を追加しない。
テンプレートで記載が求められる場合は、その指示に従う。

## 記載する内容

### タイトルと概要

- タイトルに、対象と変更後の振る舞いを含める。
- 冒頭で、解決する問題と変更の結果を伝える。
- 概要は、最終的な差分と一致させる。

### 変更内容と理由

- 主要な変更を、目的ごとにまとめる。
- レビューの判断に必要な設計上の理由を書く。
- 変更箇所を追えるよう、必要なファイルへの参照を添える。
- 作業の時系列や、ファイル一覧だけの説明は避ける。

### バグ修正

- 発生するシナリオを、前提条件と操作の順序で示す。
- 期待していた挙動と、実際の挙動を書く。
- 原因となる処理と、不具合が起きる仕組みを説明する。
- 何を変更し、その原因をどう解消したかを書く。
- 同じシナリオで、修正後にどう動くかを示す。

原因と解決方法は、コードや調査結果を根拠に書く。
原因が未確定の場合は、その旨を明示する。

### 機能実装とスコープ

- 実装した機能と、利用者ができるようになることを書く。
- 機能の一部を実装した場合は、全体の機能も説明する。
- 全体のうち、このPRで実装した部分を明示する。
- このPRのスコープ外となる部分を明示する。
- 後続のPRやIssueがある場合は、参照先を添える。

スコープ外は、関連機能のうち誤解されやすい範囲を示す。
全体の機能が、このPRだけで完成すると誤解させない。

### Before / Afterで違いを示す

- 不具合修正や動作変更では、変更前後を対比する。
- 同じ入力や操作条件で、振る舞いの違いを示す。
- Beforeには従来の状態と、その問題を書く。
- Afterには変更後の状態と、解消される問題を書く。
- テンプレート内の、概要や変更内容の項目に記載する。
- 比較する観点が複数ある場合は、表にまとめる。
- 実装が複雑な場合は、必要に応じてMermaidの図で補足する。

#### 記載例

空の検索結果を扱う修正では、同じ条件で結果を比べる。

| 条件 | Before | After |
| --- | --- | --- |
| 検索結果が0件 | エラー画面が表示される | 「該当なし」が表示される |

### 影響と移行

- 互換性や運用に影響する変更があれば説明する。
- 移行や設定変更が必要な場合は、手順を示す。
- 未解決の問題があれば、影響と残作業を書く。

## Mermaidで情報を補足する

図は、実装が複雑なときの補足として使う。
文章だけでは追いにくい処理の流れや構造を、Mermaidで示す。
テンプレート内の関連する説明の近くに図を置く。
図を追加しても、必須項目の説明は省略しない。

### 図の選び方

- フローチャート：処理の流れ、分岐、状態の変化を示す。
- クラス図：主要なクラスの責務と、依存や継承の関係を示す。
- シーケンス図：コンポーネント間の呼び出し順序を示す。

### 図に含める情報

- レビューに必要な範囲に絞り、変更の要点を示す。
- 図の前に、何を説明する図なのかを短く書く。
- コードと照合し、名前、関係、呼び出し順序を確認する。
- 修正前後を示す場合は、それぞれの状態を明記する。
- Markdownでは、言語を`mermaid`にしたコードブロックを使う。

## 構成例

テンプレートがない場合は、次の構成を基にする。
変更が小さい場合は、必要な内容を概要にまとめてもよい。
バグ修正では、シナリオ、挙動、原因、解決方法を含める。
機能実装では、全体に対する実装範囲とスコープ外を含める。
動作が変わる場合は、変更内容にBefore / Afterを含める。
影響や移行の項目は、必要な場合に加える。

```markdown
## 概要

解決する問題と、変更後の振る舞いを書く。

## 変更内容

- 主要な変更と、その理由を書く。
- 動作変更は、同じ条件でBefore / Afterを示す。

## スコープ

機能実装では、全体のうち実装した部分とスコープ外を書く。

## 影響と移行

利用者への影響と、必要な対応を書く。
```
